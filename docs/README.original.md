# Персональная афиша в MAX

Мини-приложение и один бот MAX, которые понимают запрос пользователя обычными словами, рекомендуют только реальные мероприятия, помогают компании выбрать один из трёх вариантов, напоминают о событии и дают добровольно вступить в заранее созданный чат мероприятия.

Дедлайн MVP: **30 сентября 2026 года**. Начало разработки: **23 сентября 2026 года**.

## Команда

- **Технический лидер**: frontend, MAX Bridge, бот, LLM, модерация, Docker Compose, интеграция и публикация.
- **Аня**: PostgreSQL, миграции, импорт мероприятий, API каталога, фильтры, профиль, отслеживание, задания напоминаний, совместный выбор и голоса.
- **Маша, необязательно**: Figma и UI-kit.
- **Саня, необязательно**: проверка данных, ручное тестирование и материалы защиты.

Проект обязан полностью собираться силами первых двух участников.

## P0

1. Каталог реальных мероприятий Москвы и Краснодара.
2. Фильтры по городу, дате, категории, цене и возрастному ограничению.
3. Профиль: возрастная группа, интересы, жанры и любимые исполнители.
4. Поиск естественным языком через локальную LLM со строгой JSON-схемой.
5. Объяснимые рекомендации только по событиям из PostgreSQL.
6. Источник и время последнего обновления каждой карточки.
7. Осмысленное восстановление после поиска без результатов.
8. Отслеживание событий и напоминания через бота.
9. Совместный выбор из трёх мероприятий, ссылка, голосование и победитель.
10. Один заранее созданный чат события с гибридной модерацией.
11. Seed-данные, минимальные тесты и воспроизводимый запуск.

## Зафиксированный стек

- React + TypeScript + Vite;
- Python + FastAPI;
- PostgreSQL;
- SQLAlchemy + Alembic;
- REST + OpenAPI;
- локальный Ollama с моделью `qwen2.5:3b`;
- Docker Compose;
- один бот MAX для мини-приложения, напоминаний и модерации;
- KudaGo API v1.4 как основной источник;
- PostgreSQL-таблица `jobs` и отдельный worker без Redis и Celery;
- Cloudflare Quick Tunnel для бесплатного публичного HTTPS-доступа с ноутбука.

Подробные решения находятся в [docs/DECISIONS.md](docs/DECISIONS.md), контракт API — в [docs/API.md](docs/API.md), актуальный план — в [docs/TASKS.md](docs/TASKS.md).

## Архитектура запуска

`docker compose` поднимает:

- `frontend` — собранное мини-приложение;
- `api` — FastAPI, REST и MAX webhook;
- `worker` — напоминания и фоновые задания модерации;
- `db` — PostgreSQL.

Ollama запускается на ноутбуке отдельно, чтобы образ приложения не скачивал модель при каждой сборке. API обращается к нему через настраиваемый `LLM_BASE_URL`.

Cloudflare Tunnel публикует общий вход приложения по HTTPS. Quick Tunnel выдаёт новый случайный адрес после перезапуска, поэтому перед мобильным тестом и защитой URL нужно обновить в настройках мини-приложения и webhook MAX.

## Переменные окружения

В репозитории хранится только `.env.example`. Минимальный набор:

```env
DATABASE_URL=postgresql+psycopg://app:app@db:5432/app
MAX_BOT_TOKEN=
MAX_WEBHOOK_SECRET=
MAX_BOT_NAME=
PUBLIC_APP_URL=
LLM_BASE_URL=http://host.docker.internal:11434/v1
LLM_MODEL=qwen2.5:3b
KUDAGO_API_URL=https://kudago.com/public-api/v1.4
APP_ENV=development
```

Токен бота, webhook secret и реальные пароли никогда не коммитятся.

## Первый запуск

После появления кода ожидаемый порядок будет таким:

```bash
cp .env.example .env
ollama pull qwen2.5:3b
docker compose up --build
```

Далее запускается бесплатный туннель:

```bash
cloudflared tunnel --url http://localhost:8080
```

Команды считаются окончательными только после появления соответствующих Dockerfile и `compose.yaml`.

## Правило готовности

P0 готов, если два разных пользователя могут пройти путь:

`открыть приложение → настроить интересы → найти реальные события → создать совместный выбор → проголосовать → начать отслеживание → получить сообщение бота → вступить в чат события`.

При недоступности KudaGo каталог работает на seed-данных. При недоступности LLM обычные фильтры продолжают работать, а естественный запрос обрабатывается ограниченным fallback-парсером.
