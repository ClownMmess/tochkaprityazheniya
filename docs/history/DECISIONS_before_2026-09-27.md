# Зафиксированные решения

Дата фиксации: **23 сентября 2026 года**.

Изменение решения допускается только при технической невозможности, ограничении MAX или угрозе сдаче P0 к 30 сентября.

## D-001. Один бот MAX

Используется один бот для:

- запуска мини-приложения;
- личных подтверждений и напоминаний;
- совместного выбора;
- модерации заранее созданных групповых чатов.

Причина: ожидаемая нагрузка хакатона мала. Узкое место — локальная LLM, а не количество ролей бота. Один бот означает один token, один webhook, одну настройку мини-приложения и меньше ошибок.

Маршрутизация выполняется по типу и контексту обновления:

- личный диалог — команды, подтверждения, напоминания;
- групповой чат, зарегистрированный в `event_chats` — модерация;
- неизвестный групповой чат — событие игнорируется или логируется без текста.

Разделение на двух ботов переносится в P2 и рассматривается только при ограничениях платформы или большой реальной нагрузке.

## D-002. Что означает имеющийся token

Если token получен в настройках MAX-бота, объект бота на платформе уже создан. Команда пока не написала и не запустила программную часть бота.

До начала интеграции нужно проверить:

1. имя и username бота;
2. что токен относится именно к командному боту;
3. что бот открывается с аккаунта Ани;
4. что токен не опубликован в чате, репозитории или документации.

Аккаунт Ани используется для создания тестовой группы, добавления бота и проверки мобильного сценария. Код, база и worker могут работать на ноутбуке технического лидера без личного аккаунта MAX.

## D-003. Бесплатная публикация

До защиты приложение запускается на ноутбуке через Docker Compose и публикуется через **Cloudflare Quick Tunnel**.

Плюсы:

- стоимость 0 рублей;
- не требуется VPS и публичный IP;
- выдаётся публичный HTTPS URL;
- frontend, API и webhook доступны через один адрес.

Ограничения:

- URL случайный и меняется после перезапуска tunnel;
- ноутбук должен быть включён, не спать и иметь стабильный интернет;
- Quick Tunnel используется как хакатонный демонстрационный стенд, а не постоянный production.

Перед защитой tunnel запускается один раз, новый URL записывается в настройки MAX, после чего процессы не перезапускаются без необходимости. Обязательно записывается резервное видео полного сценария.

Официальная инструкция: <https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/>

## D-004. Два города

В P0 поддерживаются:

- Краснодар — основной персональный сценарий команды;
- Москва — сценарий с более плотным каталогом и страховка для демонстрации.

Оба города доступны в KudaGo API. После первого импорта проверяется количество актуальных событий. Если в Краснодаре недостаточно данных, основная демонстрация поиска проводится по Москве, но Краснодар не удаляется из продукта.

## D-005. Источник мероприятий

Основной источник P0 — KudaGo API v1.4.

Правила:

- не использовать недокументированный scraping;
- хранить `source_id`, `external_id`, `source_url`, `source_updated_at`, `fetched_at`;
- показывать прямую ссылку на первоисточник;
- повторный импорт обновляет запись и не создаёт дубль;
- seed-набор содержит реальные выгруженные события и дату выгрузки;
- синтетические записи помечаются `is_demo=true` и не выдаются за реальные.

## D-006. Локальная LLM без оплаты

LLM запускается на ноутбуке через Ollama. Стартовая модель — `qwen2.5:3b`.

Причины выбора:

- работает локально без оплаты API;
- поддерживает русский язык;
- умеет формировать JSON;
- достаточно компактна для первого теста.

Модель выполняет только две ограниченные задачи:

1. преобразование пользовательского запроса в `SearchIntent`;
2. классификация неоднозначного сообщения в `allow`, `warn`, `delete` или `review`.

Модель не создаёт мероприятия и не определяет фактические цены, даты, адреса или льготы. Ответ проверяется по JSON Schema и Pydantic. Timeout — 5 секунд, одна повторная попытка. После ошибки используется безопасный fallback.

Официальная документация structured outputs: <https://docs.ollama.com/capabilities/structured-outputs>

## D-007. Модульный монолит

Используется один Python-кодовый базис FastAPI и отдельные процессы `api` и `worker` из одного образа. PostgreSQL используется и как база, и как надёжная очередь заданий.

Не добавляются Redis, Kafka, Kubernetes, RabbitMQ, Celery и отдельные микросервисы.

## D-008. Модерация

Порядок обработки:

1. webhook проверяет `X-Max-Bot-Api-Secret`;
2. сообщение относится только к зарегистрированному демонстрационному чату;
3. быстрые правила обнаруживают явный спам;
4. неоднозначный текст передаётся локальной LLM;
5. решение и метаданные сохраняются в журнале;
6. удаление выполняет worker с учётом лимита MAX;
7. webhook возвращает `200` до тяжёлой обработки.

Полный текст сообщения не хранится. Допустим временный текст в payload активного задания с удалением после обработки.

## D-009. Ранжирование

LLM только извлекает параметры. Сервер:

- применяет обязательные фильтры;
- рассчитывает детерминированный score;
- формирует причины из подтверждённых совпадений;
- не показывает неизвестную цену как подходящую под строгий бюджет;
- не заявляет совпадение с исполнителем без данных источника.

## D-010. Заморозка объёма

До полного P0 запрещено добавлять:

- автоматическое создание чатов;
- покупку билетов внутри приложения;
- кабинет организатора;
- социальную ленту;
- туристические маршруты;
- сложный ML-рекомендатель;
- второй источник мероприятий.

Feature freeze — вечер 28 сентября. 29 и 30 сентября предназначены для исправлений, проверки мобильного MAX, презентации и резерва.
