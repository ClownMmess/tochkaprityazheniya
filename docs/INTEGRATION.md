# Реализованная архитектура

Приоритет: текущая просьба о полном приложении и `ANYA_PRIORITY.txt`. Прежний комплект техлида требовал отсутствующий backend Ани; теперь он реализован в этом проекте. Общие контракты изменены явно и описаны в `API.md`.

## Соответствие схеме Ани

| Область | Реализация |
|---|---|
| Пользователь | users с UUID и строковым MAX ID; дата рождения и пол не сохраняются |
| Общие настройки | user_preferences: user_id, age_group_id, budget_min/max; без timestamps и TEXT[] |
| Иерархия | interests → interest_categories; user_interests и user_interest_categories |
| Организаторы | organizers, event_organizers; площадки из источников; музыканты не записываются как организаторы |
| Мероприятие | events: источник, категория, заголовок, описание, иллюстрация, возраст, ссылка |
| Сеанс | event_occurrences: даты, город, площадка, цены, статус |
| Статусы сеанса | ACTIVE / CANCELLED / POSTPONED / FINISHED |
| Tracking | tracked_events с occurrence_id, remind_at, is_notified, status |
| Уведомления | notification_jobs с user_id, occurrence_id, type, scheduled_at, status |
| Совместный выбор | group_choices, group_choice_events, group_choice_votes по occurrence_id |
| Чаты | event_chats с event_id, max_chat_id, invite_link; токенов в записи нет |
| Модерация | moderation_logs: message_id/chat_id, решение и очищенные метаданные |

Суррогатные PK — UUID; M2M-таблицы используют составные ключи, как в документе. Есть FK, уникальные ограничения, проверки цен и индексы города/даты/цены/категории. Alembic содержит явную начальную миграцию; production не использует `metadata.create_all`.

## Технические дополнения и причина

- `user_organizers` связывает выбранные пользователем площадки с профилем. Это замена прежних favorite_artists.
- `categories.interest_id` и `event_interest_categories` позволяют объяснять совпадения с интересами. Поджанры не угадываются из общего слова «концерт».
- `events.external_id`, unique(source_id, external_id), fetched_at, last_seen_at, source_updated_at и is_demo нужны для повторного импорта, достоверности источника и отделения тестовых данных. Даты проведения, цены, площадка и статус в events не хранятся.
- `event_occurrences.address`, price_text, is_free сохраняют факты первоисточника. `source_available` отличает исчезновение из выдачи источника от подтверждённой отмены. Исчезнувший сеанс не объявляется CANCELLED без основания.
- NotificationJob содержит tracking_id, dedupe_key, attempts, lease_token, locked_until, last_error_code. Дополнительные состояния processing, cancelled, review, preview обеспечивают обработку и честное отображение локальной доставки.
- `jobs` обслуживает webhook и модерацию. Уведомления находятся в выделенной таблице Ани, не копируются в jobs. Redis/Celery не нужны.
- `group_choice_events.recommendation_score` — снимок score автора для устойчивого разрешения ничьей.
- У голосов unique(choice_id, user_id) и составной FK (choice_id, occurrence_id): база не разрешает голос за чужой вариант.
- `moderation_logs.job_id` связывает журнал с заданием; в model_response сохраняются только проверенные action/reason_code/confidence/execution, не произвольный текст LLM.
- `import_runs` — история обновления источника; `event_reports` — жалобы P1.

Это дополнения к нормализованной схеме, а не возвращение бизнес-массивов или дублирование характеристик события. JSON используется только во временном payload очереди и HTTP-контрактах.

## Транзакции и доставка

Изменение tracking блокирует строку пользователя и одной транзакцией меняет подписку и задания. Повтор включения не дублирует подтверждение/напоминание. Отмена инвалидирует pending/processing задания.

Worker забирает due-задание через `FOR UPDATE SKIP LOCKED`, выдаёт lease на 90 секунд и увеличивает attempts. Завершение применимо только при совпадении lease и processing. Непосредственно перед отправкой повторно проверяются tracking, доступность и время сеанса.

MAX HTTP 429 переносит попытку (до пяти); сетевой timeout, 5xx или потеря lease переводят в review. Это исключает слепое повторение неоднозначной отправки. Абсолютная exactly-once доставка через внешний MAX API не заявлена: отправка могла уже начаться к моменту отмены.

Webhook проверяет secret, нормализует update и фиксирует job до HTTP 200. Повторный dedupe_key игнорируется. Неизвестные группы и обычные личные сообщения не сохраняются. Текст удаляется при terminal-состоянии; необработанные payload ограничены 15 минутами. Worker очищает просроченные данные и lease.

## Источник и рекомендации

В 1.1 работают KudaGo, BASE, VK Stadium, КРОП Арена и StandUp Cafe; Timepad имеет адаптер, но API вернул 403. Идентификаторы импорта стабильны, старая выгрузка не перезаписывает более свежий объект. Частичный импорт не деактивирует все отсутствующие записи. Сетевой сбой оставляет последний каталог.

LLM не создаёт карточки или факты. Она возвращает только SearchIntent / ModerationDecision. Поиск и объяснения строятся SQL и детерминированным ранжированием: интерес +40, подтверждённая подкатегория +10, выбранный организатор +20, бюджет профиля +10, базовые 10; максимум 100. Явные условия запроса дают отдельные пояснения/баллы.

Сравнение группы считает средний score автора и проголосовавших и число профилей со score выше базового. Это вспомогательная эвристика. Лидер определяется голосами и сохранённым правилом ничьей, а не меняющимся составом профилей.

## Структура кода

`models/` и `migrations/` — схема; `services/catalog.py` — каталог, ранжирование, ослабления; `services/stores.py` — DB-адаптеры и очередь; `api/routes.py` — бизнес API; `integrations/kudago/` — импорт; `integrations/llm/` и `max/` — внешние адаптеры; `bot/` — dispatcher и правила; `worker/runner.py` — фоновые задания.

Весь код работает через `app.bindings:build`. Отсутствующих бизнес-адаптеров и заглушки «нужен backend Ани» больше нет.

Расширение API 1.1 описано в API.md: новые фильтры и поля intent, выбор 2–5, пагинация поиска. Таблицы, идентификаторы ранее импортированных KudaGo-событий и старые ссылки сохранены.
