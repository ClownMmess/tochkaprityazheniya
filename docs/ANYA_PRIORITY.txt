Важное обновление архитектуры проекта.

Перед началом разработки используй эти решения как единственный источник истины для проектирования базы данных, моделей SQLAlchemy, API и бизнес-логики.

Мы пересмотрели первоначальную структуру БД и пришли к следующей финальной версии.

Не используй старую схему с массивами TEXT[], дублирующими полями или лишними сущностями.

Главный принцип:

База данных должна быть нормализованной реляционной структурой, где:
- справочники вынесены отдельно;
- многие-ко-многим реализованы через промежуточные таблицы;
- мероприятие и конкретный сеанс разделены;
- LLM не хранит и не придумывает данные;
- все реальные события приходят из источников и хранятся в PostgreSQL.

==================================================
1. ПОЛЬЗОВАТЕЛИ
==================================================

Таблица users:

Назначение:
хранение пользователя MAX.

Поля:

id UUID PK
max_user_id VARCHAR
username VARCHAR
first_name VARCHAR
last_name VARCHAR
avatar_url TEXT
created_at TIMESTAMP


Не хранить:
- дату рождения;
- пол;
- лишние персональные данные.


Возраст пользователя хранится не как дата рождения, а через возрастную группу.

Например:

18-24
25-35
35+


==================================================
2. НАСТРОЙКИ ПОЛЬЗОВАТЕЛЯ
==================================================

Таблица user_preferences:

Хранит только общие настройки.

Поля:

id UUID PK

user_id UUID FK users

age_group_id UUID FK age_groups

budget_min INTEGER

budget_max INTEGER


Убрать:

❌ interests TEXT[]
❌ genres TEXT[]
❌ favorite_artists TEXT[]
❌ created_at
❌ updated_at


Причина:
интересы имеют собственную структуру и должны храниться отдельно.

3. ИНТЕРЕСЫ ПОЛЬЗОВАТЕЛЯ
==================================================

Мы не делаем простое поле:

interests = ["театр", "музыка"]


У нас есть иерархия.


Пример:

Театр

 ├── Драма
 ├── Комедия
 ├── Мюзикл
 |
 └── Тип постановки
      ├── классическая
      ├── современная
      └── экспериментальная


Структура:


Таблица interests:

id UUID PK

name VARCHAR

slug VARCHAR

description TEXT


Примеры:

Театр
Музыка
Кино
Выставки


----------------------------


Таблица interest_categories:

id UUID PK

interest_id UUID FK interests

name VARCHAR

slug VARCHAR

description TEXT


Пример:

interest:
Театр

categories:
Драма
Комедия
Мюзикл


----------------------------


Связь пользователя:


Таблица user_interests:

user_id FK

interest_id FK


PK(user_id, interest_id)



Таблица user_interest_categories:

user_id FK

category_id FK


PK(user_id, category_id)

4. ИСПОЛНИТЕЛИ / ОРГАНИЗАТОРЫ
==================================================


Важно:

Слово "исполнители" в старой схеме было неправильным.

Нам нужны не музыканты, а организаторы мероприятий.


Например:

- театр;
- музей;
- площадка;
- организатор фестиваля.


Создать:


Таблица organizers:

id UUID PK

name VARCHAR

description TEXT

logo_url TEXT

external_url TEXT

contact_info TEXT



Связь с мероприятиями:


Таблица event_organizers:

event_id FK

organizer_id FK


PK(event_id, organizer_id)



Один организатор может иметь много мероприятий.

7. ГЛАВНАЯ СУЩНОСТЬ: EVENTS
==================================================


Важно разделять:

Мероприятие = что это?

Событие = когда это происходит?


Например:


events:

"Спектакль Гамлет"


event_occurrences:

"25 октября, 19:00, Краснодар"


--------------------------------


Таблица events:


id UUID PK

source_id UUID FK event_sources

category_id UUID FK categories

title VARCHAR

description TEXT

image_url TEXT

age_limit INTEGER

external_url TEXT



Это описание мероприятия.


Не хранить здесь:

❌ дату
❌ цену
❌ место
❌ статус проведения

12. СОВМЕСТНЫЙ ВЫБОР
==================================================


Функция:

пользователь выбирает 3 мероприятия и отправляет друзьям ссылку.


Таблица group_choices:


id UUID PK

creator_id FK users

title VARCHAR

description TEXT

public_token VARCHAR UNIQUE

expires_at TIMESTAMP

status VARCHAR

created_at TIMESTAMP



ВАЖНО:

public_token нужен только для открытия конкретного голосования.


Это НЕ:
- токен MAX;
- секрет;
- API ключ.


Пример:


https://max.ru/bot?startapp=choice_xxxxx



----------------------------


Таблица group_choice_events:


choice_id FK

occurrence_id FK


PK(choice_id, occurrence_id)


Хранит 3 выбранных события.


----------------------------


Таблица group_choice_votes:


id UUID PK

choice_id FK

occurrence_id FK

user_id FK

created_at TIMESTAMP


Один пользователь может иметь один активный голос.

==================================================
15. LLM ЛОГИКА
==================================================


LLM используется только для:


1.
Преобразования естественного запроса:


"хочу вечером недорого сходить с друзьями"


в:


SearchIntent JSON


2.
Классификации спорных сообщений в модерации.


LLM НЕ:

❌ ищет мероприятия самостоятельно

❌ создаёт мероприятия

❌ придумывает цены

❌ хранит пользователей


Все реальные данные:

KudaGo API

↓

PostgreSQL

↓

Backend

↓

Frontend

17. Требование к реализации
==================================================


Перед созданием SQLAlchemy моделей:

1.
Проверь связи.

2.
Создай миграции Alembic.

3.
Используй UUID как PK.

4.
Используй FK вместо хранения названий строками.

5.
Создай seed-данные для демонстрации.

6.
Добавь индексы для поиска мероприятий:

- city
- category
- starts_at
- price


Эта структура является актуальной версией базы данных проекта.
